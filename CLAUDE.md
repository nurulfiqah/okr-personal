# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This git repository is the **`okr` module** — one subdirectory of a much larger legacy PHP application ("odb") that lives at `C:\laragon\www\odb`. The parent `odb` app (session/auth handling, DB connection bootstrap, the shared `staff`/`staff_department`/`staff_grade`/`staff_struct` tables, etc.) is **not** part of this repo and is only reachable via relative includes such as `../lock_adv.php` and `../common/index_adv.php`. Those files exist on disk one level up from this repo but are not tracked here — do not assume they can be edited as part of this repo's history, and do not try to "fix" a missing-file error by creating stubs for them; they belong to the outer application and are shared by many other modules (`atem`, `consultcall`, etc.).

There is no build step, package manager, or automated test suite in this repo — it is plain PHP + vanilla JS + Bootstrap 5, edited and deployed as-is. There is no `composer.json`/`package.json`; nothing to install.

**PHP version:** this copy of `odb` (under `C:\laragon\www\odb`) runs PHP 8.2. Modern syntax is fine: short array `[]`, `??`/`??=`, arrow functions, etc. (This is distinct from the legacy PHP 5.3 copy at `C:\xampp\htdocs\odb`, which is a different, older codebase — the PHP 5.3 constraints only apply there, not here.)

## Architecture

OKR is a **server-rendered PHP module with a direct-mysqli JSON backend** (no separate API service, unlike `atem`/`consultcall` which proxy to Laravel APIs). Every page and the backend re-query the outer app's `staff` table directly for identity/grade/department.

OKR is pure objective-tracking: there is no RM/incentive/payout concept in this module. `okr_cards` and its sibling lookup tables (`okr_levels`, `okr_incentive_rules`) still carry their original difficulty-level/incentive-rule/payout-lock columns in the database (kept intact, unused by design — see "Retired incentive columns" below), but no page, form, or backend action in this repo reads or writes them for their original purpose anymore.

### Request flow

1. Every page-level PHP file (`index.php`, `list.php`, `view.php`, `create.php`, `edit.php`, `admin/index.php`) includes `header.php`, which: buffers output (`ob_start()`, because `lock_adv.php` echoes HTML before the redirect below can fire), requires `../lock_adv.php` (outer-app session/auth gate — sets `$grade`, `$department`, `$id_user`, etc.), sets `$connect = 1` and includes `../common/index_adv.php` (sets up `$conn` mysqli connection), then derives `$okr_permission` (`(int)$grade`) and `$okr_is_admin` (union of `staff.okr` and `staff.atem` — see SuperAdmin flag section below).
2. `download.php` does the same `lock_adv.php` + `common/index_adv.php` bootstrap independently (it doesn't include `header.php`, since it streams a file instead of HTML) — same `ob_start()`/`ob_end_clean()` trick to keep the auth redirect/`header()` calls working.
3. `admin/backend.php` and `admin/index.php` use `../../common/index_adv.php` (one extra `../` for the nesting). This page still exists and works, but `navbar.php` no longer links to it — see "Admin" below.
4. Frontend JS (`js/*.js`, one file per page, vanilla ES6, no bundler) posts `{ action, ...data }` to `backend.php` (or `admin/backend.php` for the admin-only backdate toggle), which dispatches on `$_POST['action']`/`$_GET['action']` via a flat `if` chain (see the action list in `backend.php`: `listCards`, `dashboardStats`, `getCard`, `createCard`, `stageAttachment`/`addAttachment`/`deleteAttachment`, `stageReferenceLink`/`addReferenceLink`/`deleteReferenceLink`, `updateCard`, `deleteCard`, `permanentlyDeleteCard`, `suspendCard`, `unsuspendCard`, `rateCard`, `saveDraftState`, `clearDraftState`).
5. Shared query builders, formatters, and business logic live in `lib.php` (required by `backend.php` and `header.php`'s callers) — see "Shared helpers" below. `lib.php` requires `nas_config.php` for NAS credentials/paths.

### Grade-based permission model (`staff.grade`, 0–5)

Everyone can open the module regardless of grade, including grade 0 — `header.php` no longer redirects anyone out. A grade with nothing to see (e.g. grade 0, never assigned an OKR) just gets a blank list/dashboard, since `okrScopeWhere()`'s default branch (`owner_staff_id`/`owner2_staff_id` match) naturally returns zero rows rather than erroring.

| Grade | Access |
|---|---|
| 0 | Can access the module; sees nothing (never owns a card) |
| 1–2 | See/own only their own cards (`okrScopeWhere`: `owner_staff_id` or `owner2_staff_id` match) |
| 3 | Senior management — sees own department's cards (`dept_scope` overlap) plus anything they personally issued; can create OKRs (`create.php` gate: `$okr_permission < 3`) |
| 4–5 | Company-wide visibility |
| 5 (CEO) only | Suspend/Unsuspend a card (`backend.php`: `$requester_grade !== 5 && !$requester_is_admin` blocks `suspendCard`/`unsuspendCard`) |

**SuperAdmin flag**: `okr_is_admin` (page-side) / `requester_is_admin` (backend-side) is `true` when **either** `staff.okr = 1` **or** `staff.atem = 1` (the union of both modules' flags — a SuperAdmin in either system gets full admin access in both), and bypasses every grade-based restriction in the module regardless of the user's actual `staff.grade`. Checked independently in every entry point (`header.php`, `backend.php`, `admin/backend.php`, `download.php`) — there is no shared session cache of this flag, it's re-queried from `staff` each time. The ATEM side of this union lives in `atem/header.php`'s `$_is_superadmin` and the `atem/access_control/backend.php` / `atem/admin/backend.php` `$db_is_superadmin` checks — not part of this repo, but relevant when reasoning about who has admin access here.

Card-level edit gate (`edit.php`, `backend.php`'s `updateCard`): issuer or admin. Admins may additionally set **any** Timeline status on an extended card (bypassing the normal "extended cards can only resolve as Completed/Extended/Failed" restriction) — see "OKR lifecycle / statuses" below.

### Shared helpers (`lib.php`)

- `okrCardSelectSql($where, $include_deleted)` / `okrFormatCard($row)` — the canonical card SELECT (owner/owner2/issuer names, status) and row-to-API-shape formatter. Used everywhere a card is read.
- `okrScopeWhere($requester_id, $requester_grade, $requester_dept_ids, $is_admin)` — the grade-based visibility WHERE fragment described above.
- `okrDeptIdsFromCsv($csv)` — `staff.department` is a comma-separated list of department IDs (not a single FK, same convention as `atem`/`consultcall`); this parses it to an int array.
- `okrFetchStatuses($conn, $include_recycled)` — the single DB-driven read of `okr_statuses` (id/value/description/sort_order/recycle), mirroring `okrFetchTypes`/`okrTypeValues` for `okr_types`. Every status picker/filter (Timeline dropdown in `edit.php`, `list.php`'s filter checkboxes) reads from this instead of a hardcoded status list, so an admin renaming/adding/soft-deleting a status via the lookup-table UI needs no code change. `okrTimelineAssignableStatuses($conn)` derives the Timeline-settable subset (everything except the two system-managed statuses, see below).
- Attachment/reference-link staging (`okrStageAttachment`/`okrStageReferenceLink` + their `okrFinalize*`/`okrRemoveStaged*` counterparts) — the create form stages uploads/links in `$_SESSION` before the card exists, then `createCard` finalizes them once the card row is inserted. Attachments only ever touch local disk transiently (`uploads/tmp/`, needed because `CURLFile` requires a real filesystem path) — the permanent copy lives on the corporate Synology NAS (`nas_config.php` / `lib/synologynas.php`), never in `uploads/`.
- `okrLogAudit` / `okrFetchAuditLogs` — every status change, suspend/unsuspend, rating change writes one `okr_audit_logs` row (`card_id`, `event`, `actor_staff_id`, `changes` JSON, `summary`).

### Rating

`view.php` shows a 0–5 star rating (half-star steps) in the slot the old Estimated Incentive card used to occupy — read-only for everyone, but CEO (grade 5) or admin get clickable half-star hit zones (`backend.php`'s `rateCard` action, same grade check as suspend/unsuspend). Stored on `okr_cards.rating` (`DECIMAL(2,1)`, added by `sql/add_okr_rating_column.sql`) plus `rated_by`/`rated_at`; clicking the currently-set value again clears it (`NULL`). Not gated on status or the retired `incentive_locked` column — a card can be (re-)rated any time. This is unrelated to the retired incentive system below; don't confuse `rating` with `rated_by`/`rated_at` for the old incentive-lock `locked_by`/`locked_at` columns.

### Chat Box

A per-card discussion thread (`okr_chat_messages` table, `sql/add_okr_chat_messages_table.sql`), modeled after ATEM's Chat Box (`atem/edit.php` + `atem/api.php`'s `chat-list`/`chat-send`/`chat-edit`/`chat-unsend`, which proxy to `atem-api` — a sibling module, not part of this repo, reference only). ATEM's version goes through a Laravel API; OKR has no such layer, so this is plain local mysqli instead — `lib.php`'s `okrFetchChatMessages`/`okrChatMessageEditable` and `backend.php`'s `listChatMessages`/`sendChatMessage`/`editChatMessage`/`unsendChatMessage` actions do the same job directly against `okr_chat_messages`.

- **Placement differs slightly from ATEM on purpose**: ATEM's chat lives only on `edit.php`, sendable by issuer/SuperAdmin/any ARCI member. OKR's `edit.php` is issuer/admin-only (no ARCI-equivalent access), so OKR's chat lives on **both `view.php` and `edit.php`** — visible to everyone who can view the card (same `okrScopeWhere` scope as the card itself on `view.php`; `edit.php` is already issuer/admin-only via its own page gate), postable by issuer, admin, or either of the card's owner(s) (`okrCanPostChat($card, $requester_id, $is_admin)` in `lib.php`, checked to decide whether each page renders the composer at all and again server-side in `sendChatMessage`). The two pages run independent copies of the same client-side logic (`js/view.js` and `js/edit.js` each have their own poll timer/render functions against the shared `#okr-chat-wrap` markup) rather than a shared module — matches this module's existing per-page-JS-file convention. `edit.js` additionally excludes anything inside `#okr-chat-card` from its global dirty-tracking (`markChanged`), since typing/sending a chat message is an independent, immediately-saved action, not an unsaved OKR field edit that should trigger the "leave this page?" warning.
- **Edit/unsend window**: same 60-second rule as ATEM (`OKR_CHAT_EDIT_WINDOW_SECONDS` in `lib.php`), and same "own messages only, no admin override" — `okrChatMessageEditable($conn, $message_id, $requester_id)` checks both ownership and the window server-side (never trusted from the client), backing `editChatMessage`/`unsendChatMessage`. Both `js/view.js` and `js/edit.js` mirror the same 60s check client-side purely to decide whether to show the Edit/Unsend buttons in the first place, and re-check every 5s (`refreshChatActionVisibility`) to strip them the moment the window closes without waiting for a poll.
- **Unsend is a soft delete**: `okr_chat_messages.deleted_at` is set (never hard-deleted), but `okrFetchChatMessages` always filters `deleted_at IS NULL`, so from the UI's perspective an unsent message simply disappears — same UX as ATEM's version, which appears to hard-remove from the viewer's perspective even though ATEM's own backend is presumed to soft-delete too.
- **Live-ish updates**: both pages poll `listChatMessages` every 4 seconds and do a full array resync (`JSON.stringify` compare, replace-if-different) rather than incrementally patching, so another viewer's edits/unsends propagate — same pattern ATEM uses, chosen there specifically so in-place edits show up for everyone, not just new messages.
- No audit log entry is written for chat activity (`okr_audit_logs` stays focused on card-level events — status changes, suspend/unsuspend, rating), matching ATEM's Chat Box which is likewise absent from `atem_audit_logs`.

### Owner(s) widget

Create/Edit use an ATEM ARCI-style tagging widget for Owner(s), restricted to a single "A - Accountable" role capped at 2 members (OKR has no R/C/I roles): a Department/Staff search-and-pick panel adds up to 2 owners into a member list, with an optional free-text "Purpose of joint ownership" shown once a 2nd owner is tagged. The Department picker only lists departments that actually have at least one staff member. `view.php` renders the same member-list markup read-only.

### Key Result Progress

A 2-level task list per card (`okr_key_results` table, `sql/add_okr_key_results_table.sql` + `sql/replace_okr_key_results_progress_with_status.sql`), modeled after iidas's `project_detail.php` Progression Task/Subtask widget (a sibling module, not part of this repo — reference only, not shared code). Top-level rows are Key Results (`parent_id IS NULL`, FK'd to `card_id`); each Key Result can have Subtasks (`parent_id` = the Key Result's own `id`, self-referential FK) — depth is capped at these two levels, enforced server-side in `backend.php`'s `createKeyResult` (a supplied `parent_id` must reference a row that is itself top-level, belonging to the same card). Each row has `description`, `created_by` (who added it — shown in the UI as "Created By", not user-editable), optional `start_date`/`end_date` (constrained client-side to fall within the parent OKR's own Start/End Date — `min`/`max` set from the Details/Timeline fields' current values whenever the Add/Edit Key Result modal opens, in both `create.js` and `edit.js`), and `status_id` (`TINYINT` FK into `okr_statuses` — the same lookup table the OKR card's own Timeline status uses). The table also still has an `assignee_staff_id` column (`sql/okr_key_results.sql`) — kept in the DB but **retired from the UI**: an early version of this feature had a per-row Assignee picker, replaced with the "Created By" display before this shipped widely, so the column is dead weight, never read or written by any page/action.

- **Status, not a percentage**: a Key Result/Subtask's status is one of exactly four `okr_statuses` values — Active, Completed, Completed with Excellence, Failed — via `okrKeyResultAssignableStatuses($conn)` in `lib.php` (a fixed subset, deliberately smaller than `okrTimelineAssignableStatuses()` used by the card's own Timeline field: no Draft/Extended/Completed with Extension here). The Add/Edit modal's Status `<select>` is populated from this list (`$okr_config['keyResultStatuses']`, passed from both `create.php` and `edit.php`); `backend.php` re-validates every submitted `status_id` against the same allowed-id list server-side (`stageKeyResult`/`stageKeyResultSubtask`/`createKeyResult`/`updateKeyResult`). Displayed as a colored pill reusing the card's own `.okr-pill`/`okrPillClass()` styling (`okr-pill-active`, `okr-pill-complete`, etc.) for visual consistency.
- **Auto-status**: a Key Result with subtasks shows a read-only derived status instead of its own stored value — Completed once every subtask is itself Completed or Completed with Excellence, otherwise Active (`okrFetchKeyResults`'s `display_status_value`/`display_pill_class` in `lib.php`, recomputed on every fetch — nothing is stored/cached; mirrored client-side in `create.js`'s `krDisplayStatus()` for still-staged rows that have no DB round trip yet). A leaf row (no subtasks, whether a top-level Key Result or a Subtask) has its own manual, directly-settable status; the Status field is hidden in the Edit modal once a Key Result has subtasks, since it's computed, not settable.
- **Pages**: `edit.php` has full CRUD against real rows (add Key Result, add Subtask under a Key Result, edit, delete — `backend.php`'s `createKeyResult`/`updateKeyResult`/`deleteKeyResult`, gated identically to `updateCard`: issuer or admin, and blocked while the card is Suspended). `view.php` renders the same hierarchy read-only. `create.php` supports the **full same hierarchy** (Key Results, their Subtasks, and ATEM links) before the card exists yet, entirely staged in the session: `$_SESSION['okr_draft_keyresults'][$token]` holds each top-level Key Result plus its own nested `subtasks` map (keyed by sub-token) and an `atem_id`. `okrStageKeyResult`/`okrRemoveStagedKeyResult` (top level), `okrStageKeyResultSubtask`/`okrRemoveStagedKeyResultSubtask` (nested, addressed by `parent_token` + `token`), and `okrSetStagedKeyResultAtem` (link/unlink by passing `null`) all mutate this same session structure — mirrored by `backend.php`'s `stageKeyResultSubtask`/`removeStagedKeyResultSubtask`/`stageKeyResultAtemLink`/`removeStagedKeyResultAtemLink` actions. `create.js` keeps this as one flat array (`{ token, parent_token, ... }`, `parent_token: null` for top-level) so the same rendering/auto-progress logic as `edit.js` applies locally before anything is saved. On `createCard` success, `okrFinalizeStagedKeyResults` inserts each top-level row (carrying its `atem_id`), captures its real `mysqli_insert_id`, then inserts its staged subtasks with that real id as `parent_id` — so the whole staged tree becomes real rows in one pass, alongside the existing attachment/reference-link finalization.
- Deleting a Key Result cascades to its Subtasks (`ON DELETE CASCADE` on `okr_key_results.parent_id`); deleting a card cascades to all its Key Results the same way (`ON DELETE CASCADE` on `card_id`). The same cascade is mirrored client-side for staged rows: deleting a staged top-level Key Result in `create.php` also drops its staged subtasks (the session entry they nest inside disappears with it).
- Every create/update/delete against **real** rows writes one `okr_audit_logs` row (`key_result_added`/`subtask_added`, `key_result_updated`/`subtask_updated`, `key_result_removed`/`subtask_removed`) — staging actions in `create.php` don't, since nothing durable exists yet; the audit trail starts once `okrFinalizeStagedKeyResults` inserts the real rows (which itself does not log — matching the existing no-log convention for `okrFinalizeStagedAttachments`/`okrFinalizeStagedReferenceLinks`).
- **Link ATEM**: a top-level Key Result (not Subtasks) can be linked to an existing card in the real `atem` module via `okr_key_results.atem_id` (`sql/add_okr_key_results_atem_link.sql`). This is a **plain int reference only** — ATEM lives in a separate Laravel service (`atem-api`, behind `atem/api.php`'s JWT bridge), not this database, so there is no FK and no join; `okrFetchKeyResults` just passes `atem_id` through. The "Link ATEM" icon (present in both `edit.php` and `create.php`) opens a searchable picker that calls `atem/api.php` directly from the browser (`{action: 'list-atems'}`, same-origin, same PHP session — no okr-side auth bridging needed) and lets the issuer/admin pick one of their visible ATEM cards; `backend.php`'s `linkKeyResultAtem`/`unlinkKeyResultAtem` (real rows) or `stageKeyResultAtemLink`/`removeStagedKeyResultAtemLink` (staged rows, by token) set/clear the reference. `view.php`, `edit.php`, and `create.php` all resolve the linked card's title client-side via the same `list-atems` call and link out to `atem/edit.php?id=<atem_id>` (opens read-only unless `?mode=edit` is added). All three pages pass `atemApiUrl`/`atemViewUrl` computed from `navbar.php`'s `$_navbar_atem_folder` (the ATEM sibling module folder, `atem/`) rather than hardcoding `atem/` directly in JS.

### OKR lifecycle / statuses

Statuses (`okr_statuses` table, current values — the table's `value` strings are admin-editable and have been renamed before, so **treat this list as a snapshot, not a contract**; always confirm against `okrFetchStatuses($conn)` / the live table): `Draft`, `Active`, `Completed`, `Completed with Excellence`, `Extended`, `Failed`, `Suspended`, `Completed with Extension`.

The module does not hardcode this list. `okrFetchStatuses($conn, $include_recycled)` (`lib.php`) is the single DB-driven read of the table; `okrTimelineAssignableStatuses($conn)` derives what the Timeline card's Status field can be set to directly (`edit.php`'s dropdown, `backend.php`'s `updateCard` validation) — every non-recycled status except two that are only ever reached indirectly:
- `Suspended` — no longer ever written to `result_status` at all (see "Suspend / is_suspended" below) - kept in `okr_statuses` and excluded here purely for historical/legacy-row consistency.
- `Completed with Extension` — never submitted directly; `updateCard` remaps a `Completed` submission to this status instead when the card is (or is being) extended, so the extension is visible in the stored value itself, not just a computed display label. `okrStatusDisplayLabel($status, $extended)` only previews this on the edit form's Completed option before save.

A handful of status *names* are still irreducible constants in `lib.php` (`OKR_STATUS_ACTIVE`, `OKR_STATUS_DRAFT`, `OKR_STATUS_COMPLETED`, `OKR_STATUS_SUSPENDED`, `OKR_STATUS_COMPLETED_EXTENSION`) because specific business logic keys off their identity (which status is the create-card default, which status a Completed+extended card resolves to, etc.) — not a table-shape fact, so not derivable from a query. Everything else (pill styling, dropdown/filter option lists) is driven off the table's own data (`sort_order`, `recycle`) or the shared `okrPillClass` map in `lib.php`, never re-declared per-page or per-JS-file.

- **Final Due Date**: mirrors `end_date` unless the card is `extended` *and* actually closed (`closed_at` set), in which case it follows `closed_at` instead — it does not just mirror `extended_date` the moment the Extended checkbox is ticked.
- Once extended, a card can normally only resolve as Completed/Extended/Failed (`okrPostExtensionResolvableStatuses()`); admins are exempt and may set any status. Admins are additionally exempt from the once-only Extended flag/date freeze itself (`backend.php`'s `updateCard`, `edit.php`'s checkbox/date inputs, `edit.js`'s `canEditExtended`) — a normal issuer can never uncheck Extended or change its date once saved, but admin can. This is part of admin's general full-override authority (see "Card-level edit gate" above) and is **not** exempt from the separate "locked, no further edits" gate — a card that is `is_suspended`/`Failed`/Force Terminated still blocks `updateCard` entirely for admin too (`backend.php:1101`, no bypass). `edit.js` shows a `window.confirm()` warning before submitting any save where the requester is admin and not the card's issuer (and `view.js` does the same before `updateClosureDate`), since these are silent full-overwrite paths otherwise.
- **Types / statuses** are soft-deletable lookup tables (`recycle` flag) editable only by admin, not hard-deleted, so historical cards keep referencing retired values.
- **Backdating**: `okr_config.backdate_enabled` globally allows Start/End/Extended dates to be set in the past across the module when enabled; default is disabled. Read via `okrBackdateEnabled($conn)` in `lib.php`. Writable from **two** places (both write the same `okr_config` row): this repo's own `admin/index.php` (`admin/backend.php`'s `toggleBackdate` action), and `atem/admin/index.php`'s "Allow Backdated OKRs" toggle (`atem/admin/backend.php`'s `toggleOkrBackdate` action, not part of this repo) — see "Admin" below for why both exist.

### Suspend / `is_suspended` (decoupled from `result_status`)

Suspend no longer overwrites `result_status` at all. `okr_cards.is_suspended`/`suspended_by`/`suspended_at` (three dedicated columns — `sql/add_okr_suspend_flag_columns.sql`) are the standalone source of truth for "is this card currently suspended", layered independently on top of whatever status the card already had (e.g. suspending a `Completed` card keeps showing `Completed` — the Status pill never changes to "Suspended"; a separate `.okr-pill-suspended` badge is shown alongside it instead, on `view.php`, `edit.php`'s header, and `list.php`'s table rows). `okrFormatCard()`'s `is_suspended`/`suspended_by_name`/`suspended_at` fields are what every page/JS file checks now — never compare `result_status`/`card.result_status` against `'Suspended'`/`OKR_STATUS_SUSPENDED`, that comparison can never match a card going forward (the constant and the `okr_statuses` row still exist for legacy reasons only — see below).

- **`suspendCard`** (`backend.php`): sets `is_suspended = 1` + `suspended_by`/`suspended_at`, and *clears* `closed_by`/`closed_at` ("writes off" the Closure Date — a suspend is a pause, not a completion) instead of stamping them. Still blocked on Draft and on an already-suspended card, and still limited to once per OKR's lifetime (checked via the `okr_audit_logs` `'suspended'` event, unchanged).
- **`unsuspendCard`**: just clears the flag/`suspended_by`/`suspended_at` — there is nothing to "restore" since `result_status` was never touched.
- **`forceTerminateCard`**: still sets `result_status` to `OKR_STATUS_FORCE_TERMINATED` (a real status transition, unaffected by this change) and additionally clears `is_suspended`/`suspended_by`/`suspended_at`, since the card is no longer "currently suspended" once resolved.
- Every "this card is locked, no further edits" check across `backend.php` (`updateCard`, Key Result add/edit/delete/reorder/ATEM-link) now checks `is_suspended` instead of `status_value === 'Suspended'` — each of those queries had to add `c.is_suspended`/`kr`-joined equivalents to their `SELECT`.
- **Legacy data**: any card suspended *before* this change was stored as literal `result_status = 'Suspended'` with no way to recover its pre-suspension status (the old `unsuspendCard` always reset it to `Active` and discarded whatever it had been). Those rows were migrated once, by hand, to `result_status = Active` + `is_suspended = 1` (using the existing `closed_by`/`closed_at` as `suspended_by`/`suspended_at`) — not an automatic migration, so don't assume it happens for any future legacy data found in this shape.
- `OKR_STATUS_SUSPENDED` (`lib.php`) and the `Suspended` row in `okr_statuses` both still exist (kept for id/value parity and because `okrPillClass()` still maps the string for legacy display), but neither is ever written to a card's `result_status` by any action anymore.

### Closure Date (independently editable, not just a status side-effect)

`closed_by`/`closed_at` (existing columns, repurposed) are now a real, independently-settable "Closure Date" completion marker — not purely a side-effect of an open→closed status transition. Still auto-stamped to "today" the moment a card first resolves (`updateCard`'s existing `$is_open`/`$was_open` logic, unchanged), but afterward the **Issuer, CEO (grade 5), or admin** may adjust it, within **Start Date..today**, as long as the card's status isn't Draft/Active/Failed/Suspended (`okrClosureDateLockedStatuses()` / `okrCanEditClosureDate()` in `lib.php` — the one shared permission/range check every entry point uses). Reward/incentive has no bearing here — OKR has no such concept (see "Retired incentive columns" below).

- `edit.php`: the Closure Date field in the Timeline card is a real `<input type="date">` (`min`/`max` set from Start Date/today), enabled only when `okrCanEditClosureDate()` is true; submitted as part of the normal `updateCard` payload alongside everything else.
- `view.php`: has its own standalone Closure Date field + Save button, since `view.php` has no other write path — posts to a dedicated `updateClosureDate` action (`backend.php`) rather than routing through `updateCard`'s full field set just to touch one date.
- Both call the same `okrCanEditClosureDate()`/range validation server-side — never trust the client's `disabled`/`readonly` state alone.

### Retired incentive columns

OKR previously had a full incentive/payout system (difficulty level → RM, incentive-split rules, an "Incentivised Owner" tick, People Management payout lock/unlock, a Performance/export page). That system was removed from the app; the DB was deliberately **not** altered, so `okr_cards.difficulty_level`/`incentive_rule`/`incentivised_owner_staff_id`/`incentive_locked`/`locked_by`/`locked_at`/`payout_remark`/`unlocked_by`/`unlocked_at`, and the `okr_levels`/`okr_incentive_rules` tables, still exist and still hold historical data. `createCard` still has to supply a value for `difficulty_level` (`NOT NULL`, FK into `okr_levels`, no default) — it hardcodes `1`. Do not resurrect reads/writes of these columns for new features without checking with the user first. The ATEM module's `staff_performance/` pages (separate repo) previously queried `okr_cards` directly for their own OKR reporting tab, but that integration has since been fully removed — Staff Performance is ATEM-only now and has no OKR tab, column, or query anywhere.

### Admin

`admin/index.php` + `admin/backend.php` are this module's own tiny admin area (distinct from the outer `odb` admin) — currently just the backdate toggle, gated by `$okr_is_admin` (not grade); `admin/backend.php` independently re-verifies the SuperAdmin union server-side. **`navbar.php` no longer links here** — ATEM and OKR are combined under one Admin menu, so the nav's "Admin" item points to `atem/admin/index.php` instead, whose "Allow Backdated OKRs" toggle (`atem/admin/backend.php`'s `toggleOkrBackdate` action, not part of this repo) writes the exact same `okr_config.backdate_enabled` row. This page and its backend are kept (not deleted) intentionally — they still work if reached directly, just aren't surfaced in the nav — so treat both write paths as live when reasoning about this setting, and keep them in sync if the toggle's behavior ever changes.

## Important Constraints

- Do not bypass `lock_adv.php`/`common/index_adv.php` session checks, and do not edit those files as part of OKR work — they are shared outer-app infrastructure.
- Do not create new SQL migration files under `sql/` for schema changes that have already shipped — those files are dumps of the current live schema, not a migration history. If you change a table, update the corresponding dump to match.
- Attachments must go through the staged-upload flow (`okrStageAttachment`/`okrFinalizeStagedAttachments`) and the NAS (`corpNasConnect()`), never saved permanently under `uploads/` (`uploads/tmp/` is transient only).
- Do not reintroduce reads/writes of the retired incentive columns (see "Retired incentive columns" above) without explicit confirmation — the schema was intentionally left in place for history/reversibility, not as an invitation to resume using it.
